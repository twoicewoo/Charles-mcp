# Charles MCP 2.x migration and code review

Date: 2026-10-11. Scope: Python MCP integration, live capture, reverse-analysis storage and replay, package setup, and tests.

## Verified in this change

- MCP Python SDK 2.3.0 is the current PyPI release at review time. The project requires `mcp>=2.3.0` with no upper bound and contains no MCP 1.x fallback.
- `MCPServer`, `Context`, tool schemas, and `CallToolResult` are used according to 2.x. Deprecated MCP logging calls were removed.
- A real stdio initialize/list-tools handshake succeeded with protocol `2026-07-28` and 31 tools. This did not call Charles or change its capture state.
- The reverse live reader no longer skips unreturned entries when `limit` is smaller than the current increment or when an external Charles session clear reduces the entry count. Regression tests cover both cases.
- Reverse-analysis directories and SQLite database files are owner-only on POSIX, including pre-existing permissive files when reopened.

## Open findings

### P1: Live reverse snapshots have no disk retention

`LiveAnalysisService.read()` imports the entire current session on every poll. `snapshot_history_limit` truncates only the in-memory list of capture IDs; it does not delete old captures or their body blobs from SQLite. `_snapshot_current_session()` also leaves each raw XML/native export in `tmp/` after importing it. A long or frequent capture can consume unbounded disk and leave sensitive traffic behind. See `charles_mcp/reverse/services/live_analysis_service.py` (`read`, `_snapshot_current_session`) and `charles_mcp/reverse/storage/sqlite_store.py` (no capture deletion API).

Recommendation: unlink temporary exports in a `finally` block after ingestion, implement transactional deletion of expired live captures and orphaned body blobs, and set a configurable byte/age budget. Preserve explicitly imported history captures.

### P1: Replay is a live side-effecting request without a safety gate

`reverse_replay_entry` immediately sends the stored method, URL, headers (including authorization/cookies), and body. Redirects are followed by default, and there is no host allowlist or dry-run/confirmation mode. Replaying a captured POST can repeat a purchase, login, or state change; a malicious/imported capture can redirect the agent to an unintended target. See `charles_mcp/reverse/server.py` (`reverse_replay_entry`) and `charles_mcp/reverse/services/replay_service.py` (`replay_entry`).

Recommendation: make preview/dry-run the default, require an explicit execute flag and target-host allowlist, disable redirects by default, and redact credentials from routine outputs while still permitting deliberately authorized replay.

### P2: Legacy timed recording clears the user's current session

`CharlesClient.record_session()` exports a baseline only for comparison, then calls `/session/clear` without persisting that baseline. The optional legacy `proxy_by_time` path uses this method. This contradicts the repository rule to never clear the user's session without an explicit reset request. See `charles_mcp/client.py` (`record_session`) and `charles_mcp/tools/legacy.py` (`proxy_by_time`). The tool is disabled by default, but enabling legacy tools exposes the risk.

Recommendation: require an explicit `reset_session` argument, or remove the legacy timed-recording tool. Do not silently clear the session.

### P2: Managed reverse recording can outlive its expired session

`LiveAnalysisService._prune_expired_sessions()` deletes session state without stopping a recording that the service started. The agent then loses its `live_session_id` and cannot restore the prior recording state through `stop()`. See `charles_mcp/reverse/services/live_analysis_service.py` (`_prune_expired_sessions`).

Recommendation: make expiration async and restore the recording state for managed sessions, with tests for timeout, cancellation, and process shutdown.

### P2: Shutdown may report success when Charles was never reached

`CharlesClient.quit_charles()` returns `True` for every `httpx.RequestError`, including connection failures before `/quit` was sent. See `charles_mcp/client.py` (`quit_charles`).

Recommendation: report a connection failure as failure; only treat an interrupted connection after a known successful send as a possible successful shutdown.

### P2: Detailed outputs expose captured secrets by default

`reverse_get_entry_detail` returns stored request/response headers and full body blobs, including credentials when the recording contains them. The normalizer also preserves raw sensitive values by design. See `charles_mcp/reverse/services/query_service.py` (`get_entry_detail`) and `charles_mcp/services/traffic_normalizer.py`.

Recommendation: add a redacted default view and an explicit per-call full-detail switch. Keep secrets out of logs and summary tools.

## Product and technical priorities

1. **Safety first:** replay preview, explicit execution, host allowlists, confirmation for destructive Charles controls, and secret-aware redaction.
2. **Bounded capture:** one indexed incremental stream instead of exporting/importing the entire session on each poll; byte/age retention for temporary files and live database captures; reliable recovery when an MCP client disconnects.
3. **Focused analysis:** saved filters per app/domain/device, request-flow comparison, response-schema diffs, and exportable findings with stable entry IDs and evidence links.
4. **Engineering gates:** keep the latest MCP SDK in CI, test real stdio initialization/tool calls, test Python 3.10-3.13, and benchmark 10k/100k-entry sessions for latency, memory, and disk growth.

## Verification boundary

This review tested the package and protocol locally. It did not enable Charles Web Interface, clear a real capture, replay real third-party traffic, or verify the user's Charles credentials. Those operations require separate, controlled end-to-end checks.
